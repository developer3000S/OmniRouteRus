# Руководство по настройке Kiro

Это руководство охватывает добавление учетных записей Kiro (AWS-хостируемого AI-ассистента для программирования) в OmniRoute,
с акцентом на одновременное выполнение нескольких учетных записей без конфликтов сеансов.

---

## Предыстория: Почему учетные записи Kiro могут конфликтовать

Бэкенд Kiro использует регистрации клиентов AWS SSO OIDC для отслеживания активных сеансов.
Критическое ограничение: **каждая регистрация клиента OIDC поддерживает только один активный
сеанс в один момент времени**. Когда второе устройство или пользователь аутентифицируется, используя тот же
зарегистрированный клиент, бэкенд аннулирует токен обновления первой учетной записи.

Это тот же механизм, который вызывает проблемы при выполнении `kiro-cli login` на
машине, где уже вошел в систему другой аккаунт Kiro — новая аутентификация аннулирует
токен первого аккаунта.

---

## Как OmniRoute решает эту проблему (v3.8.0+)

Начиная с версии v3.8.0, OmniRoute вызывает `registerClient()` (AWS SSO OIDC) при каждом
подключении Kiro. Это дает каждому подключению OmniRoute свою собственную выделенную регистрацию клиента OIDC. Поскольку каждая регистрация клиента независима, обновление или повторная аутентификация одной учетной записи не влияет на токен обновления любой другой учетной записи.

Изоляция применяется ко всем трем методам импорта:

| Метод импорта                                 | Статус изоляции                                                                                 |
| --------------------------------------------- | ------------------------------------------------------------------------------------------------ |
| AWS Builder ID / IDC device-code flow         | Изолирован с момента введения потока device-code                                               |
| **Import Token** (вручную вставленный токен обновления) | Изолирован с версии v3.8.0                                                                             |
| **Google / GitHub social login**              | Изолирован с версии v3.8.0                                                                             |
| **Auto-Import** (kiro-cli SQLite)             | Изолирован с версии v3.8.0 (путь SQLite уже был изолирован; резервный вариант SSO-cache теперь также изолирован) |

---

## Примечание о миграции для подключений, созданных до версии v3.8.0

Подключения, импортированные до версии v3.8.0, не имеют выделенной регистрации клиента OIDC,
сохраненной в `providerSpecificData`. Эти подключения продолжают работать, но используют общий
конечную точку обновления социальной аутентификации, что означает, что два таких подключения могут
аннулировать друг друга.

**Для получения изоляции:** удалите старое подключение из **Dashboard → Providers** и
повторно импортируйте его, используя любой из поддерживаемых потоков импорта. Все новые созданные подключения
автоматически получат свою собственную регистрацию клиента.

---

## Добавление двух учетных записей Kiro рядом

### Предварительные требования

- OmniRoute версии v3.8.0 или новее.
- Рабочая учетная запись Kiro (электронная почта + пароль, Google или GitHub).
- По желанию вторая учетная запись Kiro.

### Шаг 1: Импорт первой учетной записи

1. Откройте **Dashboard → Providers → Add Provider → Kiro**.
2. Выберите один из вариантов:
   - **Import Token** — вставьте токен обновления, начинающийся с `aorAAAAAG`.
   - **Google / GitHub login** — завершите поток OAuth в браузере.
   - **Auto-Import** — нажмите кнопку; OmniRoute читает учетные данные из
     локальной базы данных kiro-cli или `~/.aws/sso/cache`.
3. Подключение сохранено. OmniRoute автоматически регистрирует выделенный OIDC клиент для него.

### Шаг 2: Импорт второй учетной записи

Повторите шаг 1 для второй учетной записи. Поскольку каждый импорт создает отдельную регистрацию клиента OIDC,
два подключения полностью изолированы.

### Шаг 3: Проверьте, что оба подключения активны

1. **Dashboard → Providers** — оба подключения Kiro должны отображаться со статусом **Active**.
2. **Dashboard → Health** — оба подключения должны пройти проверку состояния токена.

### Шаг 4: Используйте комбо для маршрутизации между учетными записями

Создайте комбо с обоими подключениями в качестве целей, чтобы балансировать нагрузку или переходить на резервный вариант между ними:

```
kiro/kiro-dev → kiro/kiro-pro
```

См. [FEATURES.md](./FEATURES.md) и документацию по маршрутизации для настройки комбо.

## Корпоративные пользователи / IDC

Для учетных записей AWS IAM Identity Center (IDC) используйте поток **AWS Builder ID / IDC device-code**
из **Dashboard → Providers → Kiro → Device Code**. Поток device-code всегда был полностью изолированным. Для этих подключений не требуется повторный импорт.

Корпоративные пользователи, работающие в нестандартном регионе AWS, могут указать регион при импорте через API Import Token:

```bash
curl -X POST http://localhost:20128/api/oauth/kiro/import \
  -H "Content-Type: application/json" \
  -d '{"refreshToken": "aorAAAAAG...", "region": "eu-west-1"}'
```

Поле `region` по умолчанию равно `us-east-1`, если оно опущено.

---

## Срок действия клиента OIDC

Общедоступные клиенты AWS SSO OIDC обычно истекают через 90 дней
(`clientSecretExpiresAt`). OmniRoute сохраняет эту метку времени в `providerSpecificData`
для наблюдения. Если подключение перестает обновляться примерно через 90 дней, повторно импортируйте
подключение, чтобы получить новую регистрацию клиента OIDC. Автоматическая повторная регистрация при
истечении срока действия отслеживается как будущее улучшение.

---

## Устранение неполадок

### Вторая учетная запись продолжает выходить из системы

- Проверьте оба подключения в **Dashboard → Providers** и убедитесь, что каждое из них отображает непустой
  `clientId` в его JSON (видимый через значок информации). Если у какого-либо подключения отсутствует
  `clientId`, оно было импортировано до версии v3.8.0 — повторно импортируйте его.

### Ошибка импорта с "Token validation failed"

- Убедитесь, что токен обновления начинается с `aorAAAAAG`.
- Убедитесь, что OmniRoute может достичь `https://oidc.us-east-1.amazonaws.com` (или настроенного
  региона). Если вы находитесь за корпоративным прокси, установите прокси уровня провайдера в
  **Dashboard → Settings → Proxies**.

Для других проблем см. основной [TROUBLESHOOTING.md](./TROUBLESHOOTING.md).
